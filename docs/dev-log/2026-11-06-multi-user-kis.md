# 2026-11-06 실습 기록: 사용자별 KIS 키와 초대

운영자 한 명만 LIVE 계좌를 보던 구조를, 초대받은 사람이 각자 본인 한국투자증권 키를 등록해 본인 계좌를 보는 구조로 바꿨습니다. 계좌번호, 보유 종목, 금액, 키 값, 이메일, Supabase 프로젝트 주소는 이 문서에 적지 않습니다.

## 1. 출발점

- Phase 4 상태: KIS 키 한 벌을 서버 `.env`에 두고, `LIVE_OWNER_USER_ID`와 일치하는 사용자만 LIVE를 볼 수 있음
- 목표: 주변 지인이 쓰도록 배포. 지인은 각자 본인 계좌를 봐야 함
- DB 규모: 테이블 6개, 사용자별 텍스트·숫자 행이라 지인 수십 명이 써도 Supabase 무료 플랜 용량 안

## 2. 결정한 것

| 질문 | 선택 | 이유 |
| --- | --- | --- |
| 지인 키를 어디에 둘까 | 서버 DB에 암호화 저장 | 한 번 등록하면 어느 기기에서든 조회. 브라우저 저장은 기기마다 재입력, XSS 노출 위험 |
| 누구의 계좌를 볼까 | 각자 본인 계좌 | 운영자 계좌 공유는 하지 않음 |
| 계정은 어떻게 만들까 | Supabase 초대 메일 | 비밀번호를 본인이 직접 정함. 운영자가 비밀번호를 알 일이 없음 |
| 아이디 로그인 | 하지 않음(이메일 유지) | Supabase는 이메일·전화만 지원. 가짜 이메일 방식은 재설정 메일을 못 씀 |
| 환차손익 | 보류 | KIS 잔고에 매입 시점 환율이 없음. [아키텍처 문서](../architecture.md#앞으로-필요한-결정) 참고 |

## 3. 구현

- **암호화:** App Key·Secret·계좌번호를 JSON으로 묶어 AES-256-GCM으로 암호화합니다. 마스터 키 `KIS_CREDENTIAL_KEY`는 API 서버 환경변수에만 있습니다. AAD에 사용자 id와 용도를 넣어, 암호문을 다른 사용자 행으로 옮기면 복호화가 실패합니다.
- **테이블:** `public.kis_credentials`(사용자당 한 행, RLS로 본인 행만). 접근 토큰도 암호화해 같은 행에 둡니다.
- **등록 확인:** 저장 전에 실제 잔고를 한 번 조회합니다. 틀린 키·계좌는 저장되지 않습니다. 이때 발급한 토큰을 함께 저장해 바로 다시 발급하지 않습니다.
- **조회:** 로그인 토큰의 사용자 id로만 키를 찾습니다. 요청에 계좌나 키를 고르는 값이 없어 다른 사람 계좌에 닿을 경로가 없습니다. Provider는 사용자마다 하나를 재사용해 30초 조회 공유와 1분 1회 토큰 재발급 제한이 사용자 단위로 지켜집니다.
- **화면:** 설정에 "내 한국투자증권 연결" 카드(등록·다시 등록·연결 해제). 키 미등록 오류 화면에서 설정으로 바로 이동합니다.
- **초대 링크:** 초대 메일 링크(`type=invite`)를 비밀번호 재설정 화면에서 받아 첫 비밀번호를 정하게 했습니다.
- `LIVE_OWNER_USER_ID`는 앱에서 쓰지 않고, DB 통합 테스트에서 실제 사용자 권한으로 RLS를 확인하는 데만 씁니다.

## 4. 확인하며 발견한 것

### 통합 테스트가 실제 저장 데이터에 영향받음

기존 통합 테스트는 "소유자 계정에 스냅샷이 없다"고 가정했습니다. 실제로 스냅샷을 저장한 뒤라 5건이 실패했습니다. 코드 문제는 아니었습니다. API 테스트는 트랜잭션 안에서만 존재하는 임시 사용자로, RLS 테스트는 테스트 전 개수를 기준으로 비교하도록 바꿨습니다. 이때 실패 메시지에 스냅샷 금액 한 건이 터미널에 출력되었고, 이후에는 값이 나오지 않게(`--tb=no`) 실행했습니다.

### 상태 API에 사용자 정보를 싣지 않음

`/providers/status`는 로그인 없이 부르는 API라서, 서버 준비 상태(인증·DB·암호화 키)만 보여 주고 사용자별 등록 여부는 로그인이 필요한 `/kis/credentials`로 분리했습니다.
